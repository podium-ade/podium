Podium — Control Plane, Node Daemon & Networking

Design for the three infrastructure components that everything else in Podium sits on: podium-server (the host machine), podium-node (the daemon on every worker), and the tailnet fabric between them. Connectors, playbooks, and the agent adapters are out of scope here and layer on top.

1. Scope and goals

This slice delivers the ability to: install a control plane on one machine, enroll any number of worker machines over Tailscale with one command each, submit a task from the CLI that runs an OCI image with sidecars on some node, watch its logs live in a browser, and get the result back — with no connector, playbook, or agent involved yet. Everything Podium later does is "a task with a fancier spec and a fancier trigger."

Goals

  • A node is any machine with Docker and a Tailscale login. Adding capacity is one command.
  • Nodes are outbound-only. No inbound ports on workers, ever. Laptops behind NAT are first-class nodes.
  • The control plane is one container (or binary) plus Postgres plus an S3-compatible store. docker compose up is a complete install.
  • Humans reach the UI over the tailnet with no separate login — Tailscale identity is the login.
  • A single machine can be both host and node, so the smallest useful Podium is one box.

Non-goals for this slice

  • Slack/Linear/GitHub connectors, playbooks, agent adapters, the runner's step engine. (The runner binary exists here only as a log-forwarding shim; its step engine comes with playbooks.)
  • Kubernetes or Firecracker runtimes. The runtime is an interface; Docker is the only implementation now.
  • Multi-tenancy. One tailnet, one organization.

2. The four binaries

BinaryRuns onRole
podium-serverThe host machineAPI, embedded web UI, scheduler, node registry, secrets broker, artifact client. Stateless apart from Postgres and the object store; can run more than one replica later.
podium-nodeEvery workerJoins the tailnet, dials the server, advertises capacity, runs task containers via the local Docker engine, streams logs and events.
podium-runnerInside every task containerPID 1 of the task container. In this slice: runs the requested command, forwards structured events over a Unix socket. Later: executes playbook steps.
podiumDeveloper laptopsCLI: podium run, podium tasks, podium logs -f, podium nodes, podium node enroll. Talks to the server API over the tailnet.

All four are Go, cross-compiled for linux/amd64, linux/arm64, and darwin/arm64 (CLI and node). podium-node embeds the podium-runner binaries for both Linux architectures so it can bind-mount the right one into any task container without a network fetch.

3. Deployment topology

The host machine

One docker-compose.yml:

services:
  server:
    image: ghcr.io/podium/server:<ver>
    environment:
      PODIUM_DATABASE_URL: postgres://podium:…@postgres/podium
      PODIUM_S3_ENDPOINT: http://minio:9000
      PODIUM_MASTER_KEY_FILE: /run/secrets/master.key   # encrypts secrets at rest
      TS_AUTHKEY: tskey-auth-…                          # tagged: tag:podium-server
      PODIUM_TS_HOSTNAME: podium                        # → podium.<tailnet>.ts.net
    volumes: [ "server-state:/var/lib/podium" ]         # tsnet node state
  postgres: { image: postgres:16, volumes: [ "pg:/var/lib/postgresql/data" ] }
  minio:    { image: minio/minio, command: server /data, volumes: [ "minio:/data" ] }
  node:     # optional — makes the host also a worker
    image: ghcr.io/podium/node:<ver>
    volumes: [ "/var/run/docker.sock:/var/run/docker.sock", "node-data:/var/lib/podium-node" ]
    environment: { PODIUM_SERVER: https://podium.<tailnet>.ts.net, PODIUM_ENROLL_TOKEN: …, TS_AUTHKEY: … }

Postgres and MinIO are the only stateful services. Back them up and the whole control plane is reproducible from the compose file.

Storage placement matters more than CPU. Task workspaces and Docker image layers are I/O-heavy. On a homelab host, the compose volumes and the node's data_dir must sit on fast local storage (NVMe cache pool), never on a FUSE-backed array share. Document this in the install guide as a hard requirement, not a tip.

4. Networking

4.1 Tailscale as the fabric

Both server and node embed a tailnet node using the tsnet library. Each process is its own Tailscale device with its own identity — the host does not need tailscaled installed, and containers work identically to bare metal. Devices authenticate with pre-authorized, tagged auth keys:

  • tag:podium-server — exactly one device per install (more if replicated later).
  • tag:podium-node — one per worker.

A --tailscale=host mode is also supported: use the machine's existing tailscaled via the Local API instead of embedding. Useful when the host is already on the tailnet for other reasons. Same identity model, one fewer device in the admin console.

4.2 ACL policy (shipped as a documented snippet)

{
  "tagOwners": {
    "tag:podium-server": ["autogroup:admin"],
    "tag:podium-node":   ["autogroup:admin"]
  },
  "acls": [
    // workers may reach the server, and nothing else on the tailnet
    { "action": "accept", "src": ["tag:podium-node"],  "dst": ["tag:podium-server:443"] },
    // humans reach the UI/API
    { "action": "accept", "src": ["autogroup:member"], "dst": ["tag:podium-server:443"] }
    // note: nothing grants server → node, or node → node
  ]
}

This encodes the outbound-only guarantee at the network layer, independent of application code.

4.3 Identity: WhoIs replaces login

Every inbound connection to the server carries a Tailscale identity that tsnet can resolve via WhoIs(remoteAddr):

  • A connection from a tag:podium-node device is a node. The tag proves it is an authorized worker; the enrollment token (first connect) or node key (thereafter) proves which node.
  • A connection from a user device yields the user's login name. The web UI and CLI need no password, session cookie, or OAuth — the user is whoever Tailscale says they are. RBAC maps that identity to roles later.
  • Browser-facing HTTPS uses certificates Tailscale issues for the MagicDNS name (podium.<tailnet>.ts.net); tsnet handles issuance and renewal.

For local development and CI, a --dev flag listens on localhost without Tailscale and trusts a static API token. It is refused when not bound to loopback.

4.4 Transport

Node ↔ server and CLI ↔ server both use Connect RPC (protobuf schemas, gRPC-compatible, works over HTTP/1.1 and HTTP/2, browser-callable). One schema drives the Go server, the Go node and CLI clients, and the TypeScript UI client. Node streams are bidirectional; the UI consumes server-streaming for live logs. Plain JSON over HTTP is available on the same endpoints for curl and scripts.

4.5 Task container networking

Each task gets a private Docker bridge network named podium-<taskid>. Sidecars join it by their spec names (db, cache), so the environment's config points at hostnames identical on every node. The task container has internet egress but no access to the host's tailnet, the Docker socket, or other tasks. Two later add-ons keep their place in the design: an egress allow-list (implemented as a per-task network policy on the node), and a tailnet-attached task mode via a userspace Tailscale sidecar for environments that must reach internal services.

4.6 Ingress, or the lack of it

Nothing in this slice needs a public address. When connectors arrive, the documented options are Slack Socket Mode and polling (still zero ingress) or a single public route for webhooks via Tailscale Funnel — which tsnet can enable programmatically for just /webhooks/* — or an external tunnel. The server's routing keeps webhook handlers on a separate mux so exposing them never exposes the API or UI.

4.7 Without Tailscale

Transport is an interface with two implementations: tailnet (default, identity from WhoIs) and mtls (server-issued client certificates, identity from the certificate). The second exists so Podium is not unusable for teams that cannot adopt Tailscale, but it is explicitly second-tier: no MagicDNS, no automatic certs, no login-free UI. Build it only after everything else in this slice works.

5. Node ↔ server protocol

Messages

DirectionMessageNotes
node → serverEnrollOnce. Requires a valid single-use token and tag:podium-node. Returns node_id + node_key.
node → serverHelloOpens the stream. Carries labels, capacity, and the set of task IDs the node still has containers for, so the server can reconcile.
node → serverHeartbeatEvery 10s. Missing 3 marks the node unreachable; missing 12 marks it offline and expires its leases.
server → nodeAssignA task with a lease. The node must emit provisioning within 15s or the server revokes the lease and reschedules.
node → serverTaskEventOrdered per task by seq. Kinds: provisioning, pulling, started, log (stream, chunk, ts), step (from runner), artifact, exited, finished, error. Batched at ~100ms/64KB.
server → nodeAckHigh-water mark; lets the node free its replay buffer.
server → nodeCancelIdempotent. Also used for timeouts computed server-side.
server → nodeDrainStop accepting; finish running tasks; used before node upgrades.

6. Control plane internals

6.1 Packages

PackageResponsibility
server/apiConnect RPC handlers for tasks, nodes, secrets, artifacts; identity middleware (WhoIs or dev token); serves the embedded UI.
server/nodesNode registry, stream sessions, heartbeat tracking, lease bookkeeping, reconciliation on Hello.
server/schedulerLoop: claim queued tasks, match to eligible online nodes (labels ⊆ node labels, resources ≤ free), assign with lease, reschedule expired leases. Bin-packing is deliberately dumb in v1: first eligible node with most free slots.
server/storePostgres access. Migrations embedded and run on start. Queue via SELECT … FOR UPDATE SKIP LOCKED.
server/secretsEncrypted-at-rest secret store (AES-256-GCM, master key from file/env); resolution of secret names → values at assign time; short-lived token minting hooks (GitHub App comes with connectors).
server/logsIngest event batches; write recent log chunks to Postgres for live tailing; roll completed task logs into the object store; fan out to UI subscribers.
server/artifactsPre-signed upload URLs for nodes/runner, listing and download for the UI. S3 API only (MinIO, GCS interop, AWS).

6.2 Schema (essentials)

nodes(id, name, tags[], labels jsonb, capacity jsonb, node_key_hash, status, last_heartbeat_at, created_at)
enrollment_tokens(id, token_hash, labels jsonb, expires_at, used_at, created_by)
tasks(id, spec jsonb, status, priority, requested_by, node_id, lease_id, lease_expires_at,
      attempts, created_at, started_at, finished_at, exit_code, usage jsonb)
task_events(task_id, seq, kind, ts, payload jsonb)         -- append-only, PK (task_id, seq)
task_log_chunks(task_id, stream, seq, ts, bytes)           -- hot logs; pruned after roll-up
artifacts(id, task_id, name, content_type, size, object_key, created_at)
secrets(name, ciphertext, nonce, version, created_by, updated_at)
users(login, display_name, roles[], first_seen_at)         -- populated from WhoIs
audit_log(id, ts, actor, action, subject, details jsonb)

tasks.status: queued → scheduled → provisioning → running → succeeded | failed | cancelled | lost. lost is what a task becomes when its node vanishes mid-run and the policy says not to retry; the UI says so plainly instead of pretending it failed.

6.3 Web UI (this slice)

Three screens, embedded in the server binary: Tasks (list with status/node/duration, detail with live log tail and artifacts), Nodes (online state, labels, running tasks, disk/CPU, drain button), Settings → Secrets (names, versions, set/rotate — values never displayed). React + the generated Connect client. No design system decisions beyond "readable"; playbook- and connector-aware screens arrive with those features.

7. Node daemon internals

7.1 Startup

  1. Load config (/etc/podium/node.yaml or flags/env): server URL, data dir, labels, max concurrent tasks, resource caps, image cache watermark.
  2. Join the tailnet via tsnet (state in data_dir/ts) or attach to host tailscaled.
  3. Verify Docker: API version, storage driver, cgroup v2, free disk. Refuse to start on cgroup v1 (resource limits would be unreliable) with a clear message.
  4. If no node identity on disk, Enroll with the token; persist identity with mode 0600.
  5. List containers labeled podium.task; build the reconciliation set.
  6. Open the stream, send Hello, start the heartbeat ticker.

7.2 Executing an assignment

  1. Emit provisioning immediately (lease acknowledgement).
  2. Pull images concurrently with registry credentials supplied in the assignment (short-lived where the registry supports it). Emit pulling progress events; skip if digest present locally.
  3. Create network podium-<taskid> (internal bridge; egress allowed).
  4. Start sidecars, each with its readiness check from the spec (TCP port, HTTP path, or command). Wait, with a per-sidecar timeout. Sidecar logs stream as their own log streams so a failing database is diagnosable.
  5. Create the task container: image, working dir, env (spec + secrets), labels podium.task=<id>, podium.lease=<lease>; mounts: workspace volume at /workspace, the runner binary read-only at /podium/runner, an event socket at /podium/events.sock; entrypoint overridden to the runner; resource limits (CPU quota, memory + swap cap, PIDs limit); hardening: no-new-privileges, all capabilities dropped except what the spec whitelists, default seccomp, read-only rootfs when the spec allows.
  6. Attach to stdout/stderr via the Docker API and read the event socket; multiplex both into ordered TaskEvents with a replay buffer bounded by the server's Acks.
  7. Wait for exit or Cancel/timeout. On cancel: SIGTERM to the runner (which forwards to its child), 30s grace, SIGKILL.
  8. Emit finished with exit code, usage (CPU seconds, peak memory, wall time), and artifact references the runner uploaded.
  9. Teardown: stop and remove all containers on the task network, remove the network, remove the workspace volume unless keep_workspace is set for debugging (auto-pruned after 24h).

7.3 Local policies

  • Concurrency: max_tasks plus soft CPU/memory sums; the node advertises free slots, the server never over-assigns, the node refuses if it would anyway.
  • Image cache: LRU prune when disk use crosses a watermark (default 80%). Never prune images referenced by running tasks.
  • Crash reconciliation: on restart, containers with podium.task labels whose task IDs the server no longer considers assigned to this node are torn down; those still leased are re-attached and their logs resumed from the last acked seq.
  • Upgrades: podium-node upgrade downloads the new binary, sends Drain, waits for running tasks, execs into the new version. Self-update is opt-in.

8. Per-task topology on a node

9. Secrets flow

  1. An operator sets a secret by name through the UI or CLI (podium secret set GITHUB_TOKEN). The server encrypts it with the master key and stores ciphertext + version. Values are never returned by any API.
  2. A task spec lists secret names and how each should be delivered (env or file). Later, playbooks and RBAC constrain which names a task may request; in this slice, any authenticated user may.
  3. At assignment time the server decrypts, and includes plaintext values in the Assign message — which travels only inside the WireGuard-encrypted tailnet connection. Values are never written to the tasks table or event log; the audit log records names and versions only.
  4. The node holds the values in memory for the life of the task, injects them as environment variables or files on a tmpfs mount, and redacts known secret values from log chunks before forwarding (best-effort, string match; a defense in depth, not a guarantee).
  5. On teardown the node zeroes its copies. Nothing secret persists on a worker's disk.

Pluggable providers (Vault, 1Password, cloud secret managers) implement the same "resolve name → value at assign time" interface and come later; the built-in encrypted store is enough for v1 and for most small teams forever.

10. Failure modes and recovery

FailureBehavior
Node loses connectivity brieflyNode keeps running tasks and buffers events. On reconnect, Hello lists running task IDs; the server resumes streams from the last acked seq. Users see a gap-free log.
Node offline > 2 minutesLeases expire. Tasks with retry_on_node_loss: true (default for future answer/review) are requeued as new attempts; others are marked lost with an explanation. If the node returns later, its orphaned containers are torn down on reconciliation.
Node daemon crashes, containers keep runningOn restart, containers labeled podium.task are re-adopted if still leased to this node, otherwise removed.
Server restartsStateless apart from Postgres. Nodes reconnect with backoff; in-flight leases are still valid; UI subscribers reconnect and replay from the store.
Image pull fails / registry downerror event with the registry message; task fails fast with attempts+1; scheduler may retry on another node up to the spec's max_attempts.
Sidecar never becomes readyTask fails at provisioning with the sidecar's log attached. The adopter sees their database's real error, not "task failed".
Task exceeds timeout / memoryServer-side timeout → Cancel. OOM-kill is detected from the container's exit state and reported as such rather than as a generic non-zero exit.
Disk fills on a nodeHeartbeat carries disk_free; below the watermark the node prunes images and reports zero free slots until recovered. The server stops assigning to it.
Tailscale key expiryAuth keys for tagged devices are set non-expiring (tagged devices don't key-expire by default). Documented; the node logs a loud warning if its key expires within 30 days.

M1 is the proof. Server, node, runner, and CLI exchanging real messages over a real Docker engine on one laptop — with no Tailscale — validates the protocol and the execution model. Tailscale (M3) and scheduling (M4) are then additive. Build M1 before designing anything further.

13. Decisions made here

DecisionWhy
Go for server, node, runner, CLISingle static binaries, first-party Docker SDK, tsnet embedding, what the infra OSS community expects. UI stays TypeScript.
tsnet embedded by defaultZero-install networking, per-process identity, WhoIs-based login, automatic HTTPS. Host mode kept for existing tailnet hosts.
Connect RPC over WebSocket-JSONTyped contract shared by Go and TS, streaming, HTTP/1.1 compatible, still curl-able as JSON.
Postgres as queueOne stateful dependency; SKIP LOCKED is more than enough at this scale.
Runner is PID 1, mounted from the nodeAdopter images need no Podium software installed; the node controls the runner version; events are structured from day one.
Sidecars as sibling containers on a per-task networkPod semantics without Kubernetes or docker-in-docker; readiness and logs per sidecar.
Secrets in Assign, not fetched by the nodeNodes never hold credentials to the secret store; one code path; the transport is already encrypted end to end.
Nodes require cgroup v2Reliable memory/CPU limits; every supported distro has had it for years.
Dumb schedulerCorrectness first; bin-packing is an optimization with real data behind it later.

14. Open questions

  1. Node daemon as container vs. system binary. The container form (Docker socket mounted) is easiest to distribute; the systemd form is easier to reason about for reconciliation and self-update. Ship both, but which is the documented default?
  2. Rootless Docker. Support it from M2, or declare it unsupported in v1 and revisit? It weakens the "node daemon is root-equivalent" caveat but complicates networking and limits.
  3. Log retention. Hot chunks in Postgres for how long, and does the roll-up to object store happen per task at completion (simple) or on a schedule (batchy)? Proposed: per task at completion, prune hot chunks after 24h.
  4. Per-task tailnet attachment. Needed early for adopters whose environments reach internal services (a legacy API on a private host, say). Userspace Tailscale sidecar is the likely design; when does it land?
  5. Multiple servers. Nothing here prevents two podium-server replicas behind the same Postgres, but the node stream must land on exactly one. Defer, but don't preclude.
  6. Master key management. A file on the host is fine for a homelab; teams will want KMS-wrapped keys. Interface now, implementation later?
