# Step 13 — Web UI: Tasks, Nodes, Secrets (TypeScript + React, embedded)

**Milestone:** M5 ✔ · **Depends on:** 09, 10, 12 · **Design ref:** §6.3 Web UI, §4.3 identity

## Goal
A login-free web UI served by `podium-server` on the tailnet: watch tasks and live logs, see nodes, manage
secret names. Three screens, no design-system ambitions beyond readable and fast.

## In scope

### Stack (`web/`)
- **TypeScript + React 19**, Vite, React Router, TanStack Query. Connect client: `@connectrpc/connect-web` with TS types generated by
  `buf` (`protoc-gen-es`, `protoc-gen-connect-es`) into `web/src/gen/` from the same `proto/` — add to `buf.gen.yaml`; generated TS is committed.
- Styling: plain CSS modules or Tailwind — pick **Tailwind** (fast, no component library). Dark theme by default, respects `prefers-color-scheme`.
- Package manager `pnpm`; `make web` runs `pnpm install --frozen-lockfile && pnpm build` → `web/dist/`; the Go server embeds `web/dist` via
  `//go:embed` (`internal/server/api/ui.go`) with SPA fallback to `index.html` for non-API routes. `make build` depends on `make web`
  (CI installs Node 22). A `-tags noui` build skips embedding for fast Go-only iteration.
- Dev loop: `pnpm dev` proxies `/podium.v1.*` to the dev server with `Authorization: Bearer $PODIUM_DEV_TOKEN`. Over tailnet no token is needed.

### Screens
1. **Tasks** (`/`): table (id, status badge, image, requester, node, created, duration, exit code), filter by status, paginate, auto-refresh via
   polling every 5s (or a `ListTasks` watch later). Row → **Task detail** (`/tasks/:id`): spec (collapsible YAML), timeline of non-log events
   (`step`, `error`, status changes), **live log viewer** using `StreamTaskEvents` server-streaming: virtualized list, stdout/stderr/sidecar
   colouring, per-stream filter, follow toggle, search, "download raw" (artifact link when rolled up). Cancel button with confirm.
   Artifacts panel: list + download via `GetArtifactURL`. Usage (cpu s, peak mem, wall).
2. **Nodes** (`/nodes`): cards or table (name, status dot, labels as chips, running/max, cpu/mem/disk from last heartbeat, version,
   last heartbeat relative time, Tailscale device name if present), actions: Drain / Undrain / Delete (confirm). "Add a node" panel:
   `CreateEnrollmentToken` form (labels, TTL) → shows the one-line install/enroll command with the token (copy button; token displayed once).
3. **Secrets** (`/secrets`): list (name, version, updated, updated-by), Set (name + value textarea, value never echoed after save),
   Delete (confirm). Explicit copy: "Values cannot be viewed after saving."
- Header: Podium wordmark, nav, current identity (`whoami` from a small `IdentityService.WhoAmI` RPC — add to `admin.proto`), server version.
- Empty states and error toasts for every screen; loading skeletons.

### Server changes
- `IdentityService.WhoAmI` → `{login, display_name, kind}`.
- `ListTasks` gains `search` (id prefix / image substring) and `ListNodes` gains heartbeat fields if not already exposed.
- Static serving: cache headers (`immutable` for hashed assets, `no-store` for `index.html`), CSP header (self only; inline styles allowed for Tailwind runtime? — no: Tailwind is build-time, so `style-src 'self'`).

### Tests
- Vitest + Testing Library for the log viewer (ordering, filter, follow) and the enrollment-token panel.
- Playwright smoke (`web/e2e`): against the dev stack, create a task via CLI, see it appear, open it, see `hi` in the live log, node shows online.

## Out of scope
- Auth/RBAC UI, playbooks/connectors/agents screens, dashboards/metrics charts, mobile-specific layouts (must merely not break).

### The token prompt — a deliberate, recorded deviation

The step file implies "open it and it works". Under the dev transport it cannot: the server
requires `Authorization: Bearer <PODIUM_DEV_TOKEN>` on **every** Connect endpoint (only
`/healthz`, `/readyz` and `/metrics` are open) and a browser that has just loaded `index.html`
has no token. The two tempting fixes are both wrong — relaxing the server's auth for the UI
publishes the whole API to anything that can reach the port, and templating the token into the
served HTML hands it to every reader of the page, including the browser cache.

So: `TokenGate` probes once with `ListNodes`. If the call succeeds nothing is asked for (that is
the `pnpm dev` path, where the Vite proxy supplies the header). If it comes back
`Unauthenticated` the UI asks for the token, keeps it in `localStorage` under `podium.devToken`,
and re-probes; a wrong token says "Token rejected — re-enter it." A 401 from any later call
re-opens the gate (`lib/auth.ts` `onRejected`). This is the honest rendering of "the dev
transport trusts a static token". **Step 11 deletes it**: with the tailnet transport identity
comes from WhoIs, `Identify` needs no bearer token, the probe succeeds on the first try and the
gate never shows. Whoever does step 11 should also replace the hard-coded `dev` in the header
with the real login (that is the `WhoAmI` RPC the step file wants, trimmed here).

### Codegen: Connect-ES v2, no `protoc-gen-connect-es`

`protoc-gen-connect-es` does not exist in Connect-ES v2; it was folded into
`@bufbuild/protoc-gen-es` v2, which emits the service descriptors `createClient()` consumes. So
`buf.gen.yaml` has exactly one extra plugin:

```yaml
  - local: protoc-gen-es
    out: web/src/gen
    opt: target=ts
```

The binary lives in `web/node_modules/.bin`, so the Makefile now puts `$(CURDIR)/web/node_modules/.bin`
on `PATH` alongside `$(go env GOPATH)/bin`, and `make proto` depends on `web-deps`
(`pnpm install --frozen-lockfile`). `buf generate` by hand needs the same PATH entry. CI's
`proto` job installs Node and pnpm for that reason and diffs `internal/proto` **and**
`web/src/gen`.

Names to code against: enum values lose the enum-name prefix (`TaskStatus.RUNNING`,
`TaskEventKind.LOG`, `LogChunk_Stream.STDERR`), fields are lowerCamelCase, `uint64 seq` is a
`bigint`, `optional int32 exit_code` is `exitCode?: number`, and the payload oneof is
`ev.payload = { case: "log" | "exited" | …, value }` with `case: undefined` when unset.

### `go:embed` must not break a Go-only build

`//go:embed` of a missing or empty directory is a **compile error**, so a fresh clone that has
never run pnpm would fail `go build ./...`. Three things keep that from happening:

1. `web/dist/.gitkeep` is committed. `.gitignore` therefore says `web/dist/*` plus
   `!web/dist/.gitkeep`, and the old bare `dist/` pattern became `/dist/` so it no longer
   swallows `web/dist`.
2. The embed uses `//go:embed all:dist`. Without the `all:` prefix the dot-file is skipped and
   the directory is empty again.
3. Vite empties `dist/` before every build, which would delete the placeholder, so
   `vite.config.ts` carries a five-line `keepDist()` plugin that rewrites `dist/.gitkeep` in
   `closeBundle`. If you ever see `pattern all:dist: no matching files found`, that plugin is
   what went missing.

The embed lives in `web/embed.go` (package `web`), **not** in `internal/server/api/ui.go` as the
step file says: `//go:embed` can only reach files under its own directory. `internal/server/api`
holds the handler and imports `github.com/alvaroibarguen/podium/web`. `go build ./...` does not
descend into `node_modules` (no `.go` files there), and takes ~1.6 s cold.

### Serving

`mux()` no longer mounts the identity middleware on `/`. It mounts it on the three Connect
service prefixes (`/podium.v1.TaskService/`, `/podium.v1.NodeService/`,
`/podium.v1.NodeAdminService/`, from the `podiumv1connect` `…ServiceName` constants) and gives
`/` to `api.NewUIHandler`. Consequences:

- An unknown path now returns the SPA, not 401. A wrong-token RPC still returns 401 with
  `WWW-Authenticate: Bearer` — the integration suite asserts it.
- `assets/*` (Vite fingerprints everything there) gets `Cache-Control: public, max-age=31536000,
  immutable`; `index.html` and every SPA fallback gets `no-store`.
- A **missing** file under `assets/` is a real 404, not a fallback: answering a script request
  with HTML fails silently in the console.
- Every UI response carries `Content-Security-Policy: default-src 'self'; script-src 'self';
  style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none';
  form-action 'none'; frame-ancestors 'none'; object-src 'none'`, plus `X-Content-Type-Options`
  and `Referrer-Policy`. `style-src 'self'` (no `'unsafe-inline'`) is possible because Tailwind
  is compiled at build time and React applies dynamic styles through the CSSOM, which CSP does
  not govern. Adding an inline `<style>` or `<script>` to `index.html` will break the page.
- Only GET and HEAD; anything else is 405.

### Reading `StreamTaskEvents` from the browser

`hooks/useTaskEvents.ts` is the TypeScript twin of the CLI's `internal/cli/follow.go`:

- `from_seq` is exclusive, so it reconnects with the highest seq it has rendered: no gap, no
  repeat. Backoff 500 ms doubling to 10 s, reset on any event.
- **A clean end of stream means the task finished**, not that the connection dropped. That is
  when the task is re-read for its exit code. An error is not terminal — reconnect.
- Log bytes are raw and a chunk may split a line: `lib/logs.ts` keeps one incremental
  `TextDecoder` and one partial line per stream and only emits whole lines, flushing the
  unterminated tail at end of stream. Because the node uses one seq space per task, seq order is
  line order, which is what makes the accumulator's output deterministic and testable.
- `provisioning` / `pulling` / `started` arrive with the payload oneof **unset**, and replayed
  events carry `lease_id: ""`. Everything reads `ev.payload.case`, never the kind alone.
- Events are batched into React state every 60 ms so a chatty task does not re-render per chunk.
- Every non-log event also invalidates the `GetTask` query. Without that the status badge lagged
  the logs by up to one 5 s poll — a task was visibly streaming output while the badge still
  said `queued`.

Server-streaming Connect works over plain HTTP/1.1, so the browser needs nothing special; only
`NodeService.Stream` (bidi, node-only) needs h2c.

### Cancel is slow, and the UI says so

`CancelTask` returns the task **unchanged** (still `running`). With no runner the task command is
PID 1, so a default-disposition SIGTERM is discarded and the container dies at the node's 30 s
SIGKILL (exit 137); a command that traps TERM exits 143 in a couple of seconds. So the detail
page shows `cancelling…` optimistically, keeps polling, and lets the real terminal status arrive
from the node's `finished` event. Nothing blocks on the cancel response and nothing claims the
task is already cancelled.

### `ListNodes` semantics the Nodes page honours

`running_tasks` and `free_slots` are filled in only for a node holding a live stream **on that
server process**; otherwise they are 0. "Connected" is therefore `status == NODE_STATUS_ONLINE`,
never `free_slots > 0`, and the Running column shows `— / max` for a node that is not online
rather than a misleading `0 / max`.

The step file also wants CPU/memory/disk "from the last heartbeat". `ListNodes` does not expose
them: `Node.capacity` carries the *enrollment-time* `cpu_cores` and `memory_mb`, and the
heartbeat's `cpu_pct` / `mem_pct` / `disk_free_bytes` are stored but never returned. The table
shows the capacity numbers and the heartbeat age; live utilisation needs a proto change nobody
has made yet.

### Deviations, and why

1. **Connect-ES v2** instead of the step file's v1 `protoc-gen-connect-es`, which no longer
   exists. `@bufbuild/protobuf` 2.14.1, `@connectrpc/connect(-web)` 2.1.2.
2. **The token prompt** (above). The step file assumes tailnet identity; MVP-0 has none.
3. **The embed lives in `web/embed.go`**, not `internal/server/api/ui.go` — `//go:embed` cannot
   reach across directories. The handler is in `internal/server/api/ui.go` as specified.
4. **`make build` now depends on `make web`**, so CI's build job needs Node; the Go-only path is
   covered by a new `go build -tags noui ./...` step in the same job.
5. **Node 26.8.1, not the step file's Node 22.** That is what is installed on the build host.
   CI pins Node 22, which is what the step file asks for; nothing in the toolchain is
   version-sensitive beyond Vite 7's Node ≥ 20.19 floor.
6. **pnpm 11 rejects unapproved build scripts with a hard error**, and it reads the approval from
   `pnpm-workspace.yaml` as `allowBuilds: {esbuild: true}` — the pnpm 10 spelling
   (`pnpm.onlyBuiltDependencies` in `package.json`) is silently ignored. Without that file
   `pnpm install` exits 1 with `ERR_PNPM_IGNORED_BUILDS`.
7. **Vite binds `127.0.0.1`**, not its default `localhost`, which resolves to `::1` first on
   macOS and left the dev server unreachable over IPv4.
8. **No virtualization library.** `LogViewer` is a fixed-row-height window (18 px rows, 12 rows
   of overscan) in about 40 lines. It is easier to test in jsdom than a measuring virtualizer,
   and it keeps the bundle small.
9. **The Playwright smoke is not in CI.** It needs Postgres, a server, a node, Docker and the
   built CLI; the `web` CI job runs lint, typecheck, Vitest and a production build instead.
10. **No `search` field on `ListTasks`, no `IdentityService`, no artifact panel, no Secrets
    screen** — the MVP-0 trims. The proto is byte-identical to what unit B committed.

### Measured

- Bundle: **134.6 KB gzipped** total — 130.06 KB JS + 4.23 KB CSS + 0.28 KB HTML (uncompressed
  424 KB + 17.7 KB + 0.44 KB). Budget was 300 KB.
- Log latency, container write → visible in the DOM, measured against `docker logs -t`:
  **188 ms min / 233 ms median / 254 ms max** over 10 lines.
- A 50 000-line task: 34 rows in the DOM, 40 scroll jumps in 146 ms.
- Zero third-party requests: every request the page makes goes to the server's own origin.

### Open problems

- **The dev token sits in `localStorage`.** Any script that runs on the origin can read it. On
  loopback with a token the operator already has in their shell that is acceptable; it is not a
  pattern to carry into the tailnet build, which should have no token at all.
- **Nothing shows a node's live CPU/memory/disk** (see `ListNodes` above), and there is no
  Drain / Undrain / Delete: `NodeAdminService` has no such RPCs in MVP-0.
- **The tasks list has no search**, because `ListTasks` has no `search` field. Filtering is by
  status only; paging is a client-side cursor stack over `next_cursor` (Previous walks back
  through cursors it has already seen, so it cannot skip to an arbitrary page).
- **`download raw` downloads the filtered lines, not the server's stored bytes.** There is no
  non-streaming log read in the API and no artifact roll-up until step 10, so what you get is
  what the browser has accumulated.
- **The log stream holds every line in memory.** 50 000 lines are fine; a genuinely enormous task
  will grow the array without bound. A cap (or a "load earlier" seam over `from_seq`) is the
  obvious next move.
- **`prefers-color-scheme` is the only theme control.** There is no manual toggle.
